## Plan and acceptance criteria

### Implementation steps and interfaces

1. Add a pure matching entry point (suggested `src/lib/matching/match.ts`). Export `aggregateEligibility(checks)`, weighted score helpers, `evaluateMatch(role, candidate): MatchResult`, and `evaluateMatches(role, candidates): MatchResult[]`. Reuse `evaluateConstraints`; do not alter T04 semantics. Inputs are already validated domain objects.
2. Aggregate every enabled check in both directions. Any mandatory fail => blocked; otherwise any mandatory unknown => needs_clarification; otherwise eligible. Preferred failures and unknowns never block. An empty check list is vacuously eligible with both metrics null; accompanying explanation must ask for requirements, avoiding an assertion of proven fit.
3. Preference score is `100 * passed preferred weight / all preferred weight`; null if none. Evidence coverage is `100 * known (pass or fail) check weight / all check weight`; null if none. This metric measures known outcomes, not the number of evidence spans: manual known checks can count as known. Unknown checks remain in output and reduce coverage. Retain precision internally; UI rounding belongs to T07. Consider finite positive weights' extreme magnitude without introducing NaN/Infinity output; use scale-normalized sums if needed.
4. Rank copies of results by eligibility (`eligible`, `needs_clarification`, `blocked`), descending preference score, descending coverage, then candidate ID with explicit lexical comparisons (avoid environment-dependent locale ordering). Null metrics sort after numeric metrics, including zero. Do not mutate candidates, input checks, or input result arrays.
5. Add deterministic explanation templates in `src/lib/matching/explanations.ts`. Keep MatchResult schema unchanged unless a necessary shared contract is justified. Prefer a separate typed `explainMatch(result)` result exposing summary, per-check explanation records, existing questions, and metric labels/disclaimer. Retain constraint ID, direction, status, reason code, importance, and evidence references so the UI can resolve facts. Cover every reason code emitted by T04; unknown future codes must yield a neutral status-based fallback rather than invented detail. Do not invent values, names, quotes, model judgments, or facts beyond check outputs. Preserve unknown questions and classify unknowns separately from blockers; show all independent mandatory blockers. State that preferred fit is a rule-based comparison and is not a hiring probability. Null metrics say 'No preferences scored' / prompt to define requirements when no checks exist. Do not call eligibility an employment recommendation or verified qualification.
6. Add focused unit tests (`tests/unit/matching.test.ts`, `tests/unit/explanations.test.ts`) and fixture integration tests (`tests/integration/matching.test.ts`). Document public API, ordering, formulas, null/empty semantics, explanation limits in `docs/decisions/002-match-aggregation.md` or an equivalently focused decision document.
7. Update this record with actual implementation and focused checks, freeze edits, and hand off. Tester/reviewer independently reviews feature and the pre-existing workflow configuration, records full verification and approved snapshot, then marks only T05 checkboxes complete on PASS. Committer handles verified files afterward.
