## Plan and acceptance criteria

### Implementation and public contracts

1. Add pure functions under `src/lib/scenarios/` with documented exported contracts for T07: create empty scenario for role; apply validated scenario overrides to a role copy; evaluate scenario matches; compare baseline and scenario matches; detect modified IDs; reset scenario; evaluate optional single-change suggestions.
2. Validate unknown scenario input with `scenarioSchema`; reject mismatched role ID or baseline revision, duplicate patch IDs, unknown constraint IDs, and kind mismatches. Patches target employer role constraints only, never candidate preferences. Applying a patch merges value/importance/enabled changes into the matching constraint and reparses resulting role with `roleSchema`. Re-enabling a zero-weight disabled constraint must be rejected clearly rather than silently assigning a weight. Invalid scenarios must not partially mutate inputs.
3. Requirement-value edits become manual facts (`origin: manual`, `evidence: []`); preserve original source documents and unchanged requirement facts. Importance/enabled-only edits retain the untouched fact's provenance because the value still comes from its source. Clone nested arrays/objects so callers cannot mutate the baseline through returned values. Source evidence must never be fabricated for an override.
4. Detect edited constraints semantically from effective values/importance/enabled, not merely patch presence: a no-op override does not mark a constraint edited. Ignore object property order; compare list values using clearly documented set semantics (work mode/location lists are alternatives). A value equal to baseline should preserve its original fact/provenance so reset/no-op behaves consistently. Preserve role revision during a scenario; confirmation revision increments belong to T09.
5. Expose scenario evaluation against immutable baseline and candidates via `evaluateMatches`. Prefer one consistent evaluation shape containing effective role, ordered matches, and edited IDs, or document separate entry points clearly. Baseline evaluation is always recomputed from original role when needed; never rewrite baseline fixtures.
6. `compareScenarios(baselineMatches, scenarioMatches)` returns existing `ScenarioComparison` transition lists and stable changed-check IDs. Include optional per-candidate metrics/eligibility before/after through a companion typed comparison structure or separate helper for T07; preserve existing schema compatibility. Detect added/removed checks (disabled requirements), status/reason/direction/importance/weight/evidence/question changes even if eligibility is unchanged. Compare by stable IDs, never array index; ignore check/result ordering only. Reject duplicate or mismatched candidate sets rather than silently inventing absent results. Sort comparison ID lists deterministically. Eligibility transitions mean entering a category, not every candidate currently in it.
7. Reset returns an empty scenario retaining current role/revision identity; evaluating it reproduces baseline results and source provenance exactly. Reject stale scenarios; reset against a newly confirmed role can explicitly create a fresh identity.
8. Suggestions must be optional, bounded, and actually evaluated with loaded candidates. A simple API can accept caller-proposed typed single patches, validate each, and compute resulting counts/transitions plus remaining mandatory blockers and unknowns. Provide a conservative built-in enumerator for supported enabled requirement changes (e.g. mandatory-to-preferred or disable one requirement) if needed so T07 has ready suggestions. Disclose the precise change/trade-off; never claim semantic necessity to weaken requirements. Do not mutate base scenario or assume suggestions are additive: recompute the complete proposed scenario, merging/replacing one patch by stable ID. Candidate preferences remain active when employer requirements are relaxed. Only label an observed gain if recomputation proves it; zero-gain options may be omitted or shown honestly. Stable deterministic ordering, no network/clock/model.
9. Add decision/API documentation (`docs/decisions/003-scenarios.md`) explaining provenance, stale/error behavior, no-op semantics, comparison and suggestion contracts. Add focused unit/integration tests; update this record and freeze changes for independent tester/reviewer.

### Required acceptance coverage

- Deep-frozen baseline/candidates/scenario unchanged through application/evaluation/comparison/suggestions; modifying returned nested data cannot mutate baseline. Invalid patch paths leave baseline unchanged.
- Wrong role/revision, unknown/duplicate ID, wrong kind, malformed salary/date, empty patch, re-enabling zero-weight constraint rejected. Existing runtime schema validation remains authoritative.
- Value edits clear source evidence and use manual origin; untouched facts and importance-only changes retain provenance. No-op values, reordered equivalent lists, and empty overrides do not produce false edited IDs.
- Fixture remote scenario `role-work-mode` changes office to office+remote: candidate02 improves; candidate15 remains blocked by salary. Assert actual computed identities and counts, not assumed increments. Independent candidate salary/preferences/geography remain active; baseline counts unchanged.
- Mandatory-to-preferred and disabling cover changed eligibility, scores, known-outcome coverage, removed checks, and unanswered questions. No removed blocker hides another active blocker.
- Comparison records metric changes even with identical eligibility through companion API; check-ID differences include removed/added checks and changed importance with same pass status. Reordered inputs compare identically. Mismatched/duplicate candidate lists rejected.
- Reset yields deeply identical baseline matching/provenance and no edited IDs. Repeated scenario/suggestion evaluation and candidate input shuffles produce same outputs.
- Suggestion reported counts equal direct `evaluateMatches` on resulting effective role; existing override merging works; all remaining blockers remain visible; no unsupported claim or instruction to maximize counts by removing requirements. At least one known single-change result is asserted independently.
