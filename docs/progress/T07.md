## Plan and acceptance criteria

### Implementation sequence and contracts

1. Add pure versioned storage helpers (`src/lib/storage/persistence.ts`) and tests first. Envelope `{ schemaVersion: 1, role: Role, scenario: Scenario }`, a single documented stable storage key, and functions to decode/encode validated state and load/save/clear via an injected storage interface. Reparse role and scenario, use `applyScenario` to reject stale revision/ID/kind errors. Distinguish missing, malformed, unsupported version, stale scenario, and unavailable/quota-failed storage. Safely use sample baseline on invalid saved role; a valid saved role with stale/invalid scenario can retain role and reset overrides with visible notice. No prior envelope version exists, so explicitly reject future/unsupported versions rather than inventing a migration. Never persist candidates, result arrays, selections, draft text, or credentials.
2. Add client dashboard entry under `src/components/dashboard/` composed from server `src/app/page.tsx`. Use serializable validated fixture props or load validated static fixtures within the client. State holds confirmed role, scenario, selected candidate, filter/search, and restore/save status; matching results/counts/details are derived via existing matching/scenario APIs, not duplicated mutable state. Start with deterministic initial UI; restore storage after mount and avoid saving sample state over stored values before restoration completes. Disable conflicting actions while restoring and expose a brief loading status. Catch storage failure without losing a functioning no-key sample demo.
3. Build calm, polished recruiter layout: pale neutral canvas, forest-green accents, clear typographic hierarchy, white bordered panels, readable badges, summary above results. Desktop role/scenario sidebar plus candidate results; detail opens accessible overlay/dialog or side panel. Narrow layouts stack controls and results, with full-width detail. Keep fictional-data and independent-project notice visible. Use text labels alongside statuses, percentage labels as rule-based preferred fit/known-outcome coverage, and null labels from T05; no probability language. Provide Load fictional sample and Clear local data with documented distinct behaviors.
4. Role controls show confirmed baseline title/revision and typed scenario edits for every existing constraint: skill text, salary min/max/currency/open-bound flags, work-mode multi-select, location IDs, ISO start date; importance and enabled state. Use local controlled field drafts so partial/invalid numbers/dates are not applied as corrupt overrides. Validate on apply or appropriate completed input; finite controls recompute immediately. Label errors, retain invalid input for correction, and keep last valid results. Edited indicators use semantic T06 IDs. Reset scenario clears overrides and field drafts, reproducing baseline. Do not implement extraction or its confirmation flow yet; baseline editor is optional, sample baseline + scenario controls satisfy role editing. If manual baseline confirmation is introduced, validate explicitly, increment revision, and clear scenarios atomically.
5. Summary compares baseline/scenario eligible, blocked, clarification counts and current delta for loaded 25 profiles; cards expose candidate name, eligibility, score, coverage, blockers/unknowns and baseline change. Support eligibility filters, search, and honest no-results empty state with clear reset action. Optional suggestions use `evaluateSuggestions`, display exact trade-off and recomputed counts; applying one uses returned validated scenario, never concatenates independent gains.
6. Candidate detail separates employer requirements and candidate preferences, renders all check statuses/reason templates/questions (including unknowns for blocked candidates), and identifies changed/removed checks. Resolve evidence by source ID across current effective role and selected candidate sources; render source text with React text nodes and `<mark>` over exact UTF-16 slice, including surrounding context and source label. Never use HTML injection or guessed quote matching. Value overrides visibly say manual/no source quote; unchanged original facts retain source labels. Clarification questions remain actionable text, not false rejection claims.
7. Accessible interactions: labels for all fields/buttons; visible focus; keyboard opening detail; named dialog, initial focus, Tab/Shift+Tab containment where modal, Escape close, and focus return to opener. Status updates use a restrained live region. No horizontal overflow at 390px; long source IDs/text wrap. Respect reduced motion if animations are added. Existing skip link target remains valid.
8. Add `@playwright/test` dev dependency and lockfile, `playwright.config.ts`, `test:e2e` script; use Chromium or installed Chrome/Edge fallback explicitly documented. Use production webServer on isolated port where practical; build before browser suite. Exclude `tests/e2e/**` from Vitest's broad include. Ignore Playwright reports/test-results. Screenshots saved to gitignored artifacts, not source control. Do not treat package installation as browser verification.
